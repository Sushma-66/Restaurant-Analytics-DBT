# Hoshi Kitchen — Analytics Warehouse

Analytics engineering project for **Hoshi Kitchen**, a (fictional) five-branch
Japanese restaurant group in the UK. It turns nightly POS and loyalty-CRM exports
into tested, documented tables for finance and marketing.

**Layers**

| Layer | Materialisation | Purpose |
|---|---|---|
| `staging` | view | 1:1 with sources. Rename, type, de-duplicate, clean. No joins (except lookup seeds). |
| `intermediate` | ephemeral | Re-usable business logic: point-in-time costing, payment pivots, order enrichment. |
| `marts/core` | table / incremental | Conformed facts & dimensions (`fct_orders`, `dim_members` ...). Contract-enforced. |
| `marts/finance` | table | Daily branch sales (the EOD report) and till reconciliation. |
| `marts/marketing` | table | RFM segments, cohort retention, promotion profitability. |

All data is synthetic, generated by `scripts/generate_raw_data.py`.

{% docs order_id %}
Natural key of an order from the POS, prefixed with the branch code (e.g. `SOK-00012345`).
{% enddocs %}

{% docs branch_code %}
Three-letter branch code (`SOK`, `NST`, `SOL`, `BRS`, `LEI`). Upper-cased in staging because the POS export is inconsistent.
{% enddocs %}

{% docs member_id %}
Loyalty member identifier. NULL when the customer did not scan a loyalty card.
{% enddocs %}

{% docs net_sales_amount %}
Gross food & drink sales minus discounts, **VAT-inclusive**, excluding service charge. This is the headline "sales" figure used by operations.
{% enddocs %}

{% docs net_sales_ex_vat %}
Net sales with the 20% UK VAT backed out - the revenue figure finance reports on.
{% enddocs %}

{% docs is_revenue_order %}
True only for `completed` orders. Voided and refunded orders are kept for audit but excluded from sales.
{% enddocs %}

{% docs is_cost_estimated %}
True when the order pre-dates the menu-price snapshot, so cost was estimated from the current cost-to-price ratio rather than the historical cost.
{% enddocs %}
